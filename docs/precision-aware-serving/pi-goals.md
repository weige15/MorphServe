# Precision-aware continuous-batching research: Pi goals

Source baseline: `weige15/MorphServe@c370077a6ecf2ef83a266e9a240f11764d9984c7`.

Decision: keep `main` as the preserved MorphServe reproduction/evidence line. Start the novel research in a separate sibling repository derived from the reusable SwiftLLM/runtime substrate, not by rewriting the v6-v11 history. If repository creation is unavailable, use this bootstrap branch only as a temporary staging area and report the blocker.

The goals below are sequential. Do not start Goal 2 until Goal 1 has either established a measurable structured precision signal or reported that the premise is not supported. Do not start Goal 3 until Goal 2 has a correct heterogeneous-precision serving prototype with explicit batching-cost measurements.

## Goal 1 — establish whether query-dependent Q/K/V precision structure is real

```text
/goal --tokens 80000 Produce the strongest evidence-backed characterization of query-dependent mixed-precision structure inside transformer attention and MLP projections, using the reusable SwiftLLM/AWQ-Marlin/runtime substrate in weige15/MorphServe@c370077a6ecf2ef83a266e9a240f11764d9984c7, the preserved MorphServe evidence and paper under references/, the QAQ paper supplied by the researcher when available locally, current public literature only when needed, and the available GPU/test environment. Keep the existing MorphServe main history unchanged; first create or prepare a clean sibling research repository that records the exact MorphServe source commit and copies only code/tests/docs needed for the new work rather than historical raw benchmark archives. Attempt to answer, rather than assume, whether precision sensitivity varies materially by query, layer, attention-vs-MLP, and especially Q/K/V/O projection; determine the finest structured granularity that can be executed without arbitrary per-element irregularity; audit AWQ rescaling/norm coupling before mixing FP16 and quantized projections so no invalid hybrid path is treated as evidence; implement the minimum static instrumentation needed to run correct per-projection precision ablations; compare at least uniform FP16, uniform W4, layer-wise mixed precision, MHA-vs-MLP mixed precision, and feasible Q/K/V/O mixed profiles on representative prefill/decode shapes and multiple query/task classes; measure quality/error deltas, latency/kernel cost, memory footprint, and whether the preferred precision profile changes across queries. Use held-out queries for any sensitivity rule chosen from calibration data, retain raw per-query/per-profile results, exact commands, environment, commit hashes, and seeds, and avoid training a router until the existence and repeatability of query-dependent structure are established. Verify mathematical correctness of every mixed path, static-output equivalence where equivalence is expected, existing regression tests, targeted new tests, repeated GPU measurements, and an auditable analysis that quantifies within-query versus between-query variation and identifies whether Q/K/V asymmetry is large enough to justify runtime scheduling. If an exact per-projection hybrid is blocked by AWQ representation coupling or kernel limitations, test the nearest mathematically valid structured alternative and document the gap rather than silently approximating it. End with a report that separately lists CONFIRMED FINDINGS, SUPPORTED BUT UNCERTAIN FINDINGS, BLOCKED QUESTIONS, and REMAINING UNCERTAINTY, and include a GO/NO-GO decision for building a precision-aware continuous-batching runtime based on predeclared evidence thresholds justified before inspecting final held-out results.
```

## Goal 2 — build the smallest correct precision-aware continuous-batching runtime

Run only if Goal 1 is GO.

```text
/goal --tokens 100000 Produce the strongest evidence-backed precision-aware continuous-batching prototype, using the clean research repository and validated precision profiles from Goal 1, the existing SwiftLLM continuous-batching/strict-FCFS engine, AWQ-Marlin and FP16 kernels, segmented KV support, and available GPU profiling tools. Attempt to serve concurrent requests whose validated precision demands differ without collapsing every request to the batch maximum precision; represent precision demand as an explicit request/runtime state, implement the smallest correct scheduling/execution mechanism first (for example precision-compatible grouping or microbatching), and measure the batching fragmentation and kernel-launch cost it introduces. Only attempt more complex shared-low-bit-plus-high-bit-refinement or custom heterogeneous kernels if measured evidence shows the simpler design cannot meet the target and a mathematically valid nested representation is available; do not invent per-element mixed-precision kernels merely for novelty. Preserve request IDs, exactly-one-prefill behavior, KV/position state, FCFS/fairness semantics unless a deliberate alternative is preregistered, and the existing state-preserving morphing invariants. Attempt both prefill and decode, mixed prefill/decode batches, multiple sequence lengths, and at least two precision profiles that differ at Q/K/V or the finest granularity Goal 1 validated. Compare against uniform FP16, uniform W4, static layer-wise mixed precision, the existing MorphServe-style process-wide dynamic state, and an oracle or offline grouping baseline where feasible. Verify end-to-end correctness, output/quality bounds, scheduler invariants, no request loss/duplication, KV integrity, GPU memory accounting, throughput, TTFT, TPOT, batch occupancy, precision-induced fragmentation, transition/grouping overhead, and repeated-run variance. Freeze workload and decision thresholds before final confirmation runs, keep exploratory and confirmatory evidence separate, and retain exact raw traces and regeneration commands. End with a report that separately lists CONFIRMED FINDINGS, SUPPORTED BUT UNCERTAIN FINDINGS, BLOCKED QUESTIONS, and REMAINING UNCERTAINTY, and give a GO/NO-GO decision on whether heterogeneous precision can coexist with continuous batching at a useful quality/latency/throughput point rather than merely functioning.
```

## Goal 3 — joint query/workload precision control and paper-quality evaluation

Run only if Goal 2 is GO.

```text
/goal --tokens 120000 Produce the strongest evidence-backed end-to-end research result for joint query-aware and workload-aware precision scheduling in continuously batched LLM serving, using the validated heterogeneous-precision runtime from Goal 2, the current MorphServe workload-control substrate and segmented KV mechanisms, the query-sensitivity evidence from Goal 1, real or public burst traces already used by the project, representative long-context and reasoning/QA/summarization workloads available in the environment, and relevant published baselines. Attempt a controller that decides precision from both request/query evidence and system pressure rather than from either signal alone; explicitly study how weight/projection precision, batch composition, KV capacity or KV precision when feasible, prefill/decode phase, and SLO pressure interact. Compare against FP16, static W4, static mixed precision, MorphServe-style workload-only adaptation, QAQ-style query-only precision when reproducible or a clearly labeled faithful proxy, and the Goal-2 scheduler without adaptive control. Test whether query-aware precision actually improves SLO-goodput or quality at fixed resource/SLO budgets, whether it avoids over-provisioning easy requests without harming difficult ones, whether Q/K/V-specific choices remain useful under real batching, and whether any gain survives controller overhead, tail latency, memory pressure, and repeated burst cycles. Pre-register primary metrics and confirmation workloads before final runs; use paired/repeated experiments where practical; retain raw traces, exact environment, code commit, model/checkpoint hashes, seeds, quality outputs, and regeneration scripts. Verify request/state/KV correctness, controller stability and false-entry/chatter behavior, quality on held-out content, TTFT/TPOT/throughput/SLO-goodput, HBM/KV capacity, precision distribution, batching efficiency, controller cost, and statistical uncertainty. Do not claim generality beyond tested models/GPUs/workloads, and do not force a positive result: if query-dependent fine-grained precision does not beat simpler workload-only or static policies after full systems costs, characterize that negative result rigorously. End with a report that separately lists CONFIRMED FINDINGS, SUPPORTED BUT UNCERTAIN FINDINGS, BLOCKED QUESTIONS, and REMAINING UNCERTAINTY, plus a concise claim matrix showing exactly which proposed paper claims are supported, falsified, or still untested.
```

## Why the split exists

Goal 1 is a falsification/measurement stage: it prevents building a large serving system around an unproven assumption that Q/K/V or per-query precision heterogeneity is useful. Goal 2 isolates the systems problem of heterogeneous precision inside continuous batching. Goal 3 only adds the adaptive controller after the numerical and systems premises have both survived measurement.
